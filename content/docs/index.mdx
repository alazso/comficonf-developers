ComfiConf gives server owners a web editor for plugin settings. Your plugin defines what can be configured and how
a change is activated; ComfiConf provides the interface. You describe your settings once with the Java API, and
ComfiConf generates the editor, checks every submission against your description, shows the owner a review of
each change, and hands the change to your plugin.

## What an integration gives your plugin

- **An editor without web code.** Text, toggles, numbers with sliders, dropdowns, multi-selects, a material picker,
  nested groups and repeatable entries with bulk editing, all generated from your schema.
- **Validation before your code runs.** The bridge checks types, ranges, patterns, choices, required values, list
  sizes and duplicate keys. Your `validate` callback only adds the rules a schema cannot express.
- **A review step.** The owner sees every change with its old and new value, your warnings and errors, and which
  changes need a restart, before anything is saved.
- **Conflict detection.** Revisions tell the bridge when your file changed outside ComfiConf, so stale values are
  refused instead of overwriting newer ones.
- **Safe saves.** `SafeFileWriter` re-checks the revision under a lock, keeps backups and replaces files
  atomically. `SectionMapper` maps a Bukkit `config.yml` to your schema and back, keeping comments and keys the
  schema does not declare.
- **Secrets that stay on the server.** Sensitive fields never leave it; write-only fields can be replaced from the
  editor without being shown.

## How a change flows

```text title="Components"
web editor  --HTTPS-->  backend  <--WebSocket (outbound from the server)--  ComfiConf bridge plugin
                                                                                   |
                                                                       your plugin (ConfigProvider)
```

1. The server owner installs the **ComfiConf bridge plugin** (plugin name `ComfiConf`). It opens an outbound
   WebSocket to the backend, so no port is opened on the Minecraft server, and is paired with the owner's account
   once with `/comficonf pair`.
2. Your plugin registers a **configuration resource** with the bridge: a stable id, a display name and a
   `ConfigProvider` with four callbacks.
3. When the owner opens your resource, the bridge calls `describe()` (the schema) and `read()` (current values).
   The editor is generated from the schema; there is no plugin-specific web code.
4. When the owner applies a change, the bridge checks the submitted values against your schema, computes the
   changes, calls your `validate()` for rules the schema cannot express, and finally `apply()`, where your plugin
   persists the values and activates them. The bridge reports your truthful outcome back to the editor.

## What stays under your control

<Callout title="Not a remote file editor">
  The bridge never reads or writes your files and exposes no file, console or command access to the backend.
  Everything goes through your callbacks, so your plugin keeps full control over storage, validation and
  activation.
</Callout>

- **Your plugin owns its files.** Only declared keys are ever sent to the editor; everything else in your file
  stays private, and your `apply` preserves it.
- **Your plugin decides what is applied.** It can reject values, report warnings, or save a change that waits for
  a restart. The editor shows exactly the outcome you return, and `APPLIED` means the values are stored and
  active.
- **Your plugin works without ComfiConf.** The API is a soft dependency; without the bridge, your plugin starts and
  runs as before.
